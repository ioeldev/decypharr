---
title: Health Checker & Repair
description: Per-entry health tracking with scheduled sweeps and on-demand rechecks.
---

The health checker tracks the state of every entry in your library and runs scheduled sweeps that re-probe only the entries that actually need checking. Each entry carries a health status visible in Browse, and you can force a recheck of a single entry at any time — independent of the global schedule.

## Concepts

### Entry health

Every entry has exactly one health record with one of these statuses:

| Status        | Meaning                                                        |
|---------------|----------------------------------------------------------------|
| `healthy`     | All probed files are reachable.                                |
| `broken`      | At least one file failed its probe.                            |
| `repairing`   | A sweep is currently probing or fixing this entry.             |
| `unknown`     | Probe was inconclusive (no files broken, none confirmed OK).   |
| `stale`       | Last check is older than `recheck_interval`.                   |
| `unsupported` | The entry has no probe path on this protocol.                  |

Each record also stores the file fingerprint, last-checked / last-OK / last-failed timestamps, the next-due time, and the list of broken files (with their Arr IDs when the source is Arr).

When an entry's file set changes, its fingerprint is invalidated and the entry is marked **dirty**, forcing a re-probe on the next sweep.

### Sweeps

A **sweep** is a single pass that selects candidate entries, probes them, and (when `auto_repair` is on) attempts to fix the broken ones. Sweeps are recorded as **runs** (history-only — you cannot create a run by hand).

A sweep does not scan your whole library every time. It selects only entries where:

- status is not `healthy`, **or**
- the entry is dirty, **or**
- the entry has never been checked, **or**
- the entry's `next_check_due_at` has passed.

Healthy entries that haven't changed since the last successful check are skipped.

### Single-entry recheck

You can force a recheck on any one entry from the Browse UI or the API. This works even when the global health checker is disabled and does not produce a run record. Repairs should be triggered through the Arr integration.

## Library read audit

The default checker probes provider APIs for entries managed by Decypharr. A
library read audit instead enumerates imported files directly from Sonarr and
Radarr, including files whose original torrent is no longer in Decypharr.
It opens the library path in Decypharr's container and reads **64 KiB**. Mount the
same library directories at the same paths used by the Arrs and Plex; absolute
symlink targets must resolve in Decypharr's container too.

Select **Audit library reads** in the Run modal for a one-off audit. Enable the
same setting in Configuration to use this mode for scheduled runs
(`repair.library_audit: true`). It replaces the provider probe for that run.
The Arr selection, skip-repair flags, recheck interval, ignore-last-checked,
auto-repair and stop schedule apply. The source and torrent/NZB protocol filters
do not apply: this mode checks the imported paths regardless of their original
transport. Counts represent individual library files rather than torrent folders.

Reads use `repair.workers` concurrent workers (default 5), with a 30-second
per-file deadline and no fixed delay between files. Start with a small worker
count: mount read-ahead can transfer more than the 64 KiB sample. Automatic
restoration and recovery submission remain serial; Arr recovery dispatch is
paced separately by the Repair queue settings.

With **Repair Whole Season** enabled (`repair.replace_whole_season: true`), Sonarr
files are read sequentially within each series/season. After the first confirmed
broken file, the audit skips the remaining files in that season; other seasons
and movies continue concurrently. Run history reports these avoided reads as
`skipped_season`, separately from confirmed broken files. Unread files retain
their previous health and check timestamps. The confirmed incident is enough for
auto-repair or **Fix broken** to replace all imported files in that season and
search for a season pack, with an episode-search fallback covering the whole
season snapshot. If auto-repair restores the original file, the audit continues
checking the season. Inconclusive reads do not trigger this shortcut.

The mount must be available before probing starts (the built-in DFS mount must
also expose its `version.txt` marker). An unavailable library parent directory,
permission error or other inconclusive I/O result is **unknown**, not repairable.
A timeout stops dispatch and cancels the other probes. Filesystem calls still
blocked retain their worker slots, including across subsequent runs and changes
to the worker setting, until they return.

A missing target, a file smaller than the sample, an incomplete read, or an HTML/XML
error document becomes **broken** only if confirmed by a
second probe. Results appear in **View broken** with the library path and owning
Arr file ID. They use independent `library:` health keys, so a successful provider
API check cannot overwrite a failed library read. The recheck action repeats the
filesystem audit, even when the original torrent no longer exists. Results for
Arr file IDs that disappear after replacement are removed after a successful
library enumeration. Clear-broken clears audit findings without deleting files
from the mount.

With auto-repair enabled, or when **Fix broken** is selected:

1. Recheck the mount and library path; skip replacement if it is readable again.
2. If the symlink maps to an existing torrent, try the original torrent through
   Decypharr's existing reinsertion mechanism and verify the library read again.
3. If the path is still confirmed broken, queue the existing durable Arr recovery
   using the exact file ID and path. Sonarr uses replacement **season pack first**,
   then **EpisodeSearch** when no eligible pack exists. Radarr searches the owning
   movie. Files without an indexed torrent use verified Arr-library recovery.
   Unindexed episodes of the same Sonarr season remain queued and dispatch one
   at a time. Before dispatch, a queued orphan is checked against the Arr file
   identities; a replacement imported by an earlier pack recovery satisfies it
   without another delete/search.

A successful sample establishes only that the beginning is readable now. It can
come from cache and does not validate the complete movie, decoding, seeking, or
Plex networking. DFS chunking/read-ahead can download substantially more than
64 KiB. The audit covers files still declared imported by an Arr; loose symlinks
with no Sonarr/Radarr file record are outside this mode.

For an initial detection-only run through the API:

```http
POST /api/repair/run
Content-Type: application/json

{
  "library_audit": true,
  "ignore_last_checked": true,
  "auto_repair": false
}
```

## Repair dispatch queue

**Fix broken** and auto-repair enqueue durable Arr recovery jobs. Completing the
health-check run means recovery has been requested; it does not mean every media
file has been replaced. Track actual imports in **Arr Reacquisition**.

New automatic repair jobs share a global dispatch policy across Sonarr and Radarr:

| Setting | Default | Meaning |
| --- | --- | --- |
| `repair.queue_interval` | `10s` | Minimum time between new repair dispatch slots. |
| `repair.queue_batch_size` | `50` | Dispatch slots per batch. |
| `repair.queue_batch_pause` | `5m` | Minimum cooldown after each batch, measured from its last dispatch. `0s` disables the extra cooldown. |
| `repair.queue_max_active` | `10` | Maximum active repair jobs, including searches and pending downloads/imports. Deferred retries and jobs needing attention do not occupy a slot. |
| `repair.queue_paused` | `false` | Hold new repair jobs and scheduled retries in the queue. |
| `repair.queue_search_timeout` | `5m` | Bound an Arr recovery attempt; a long-running remote search is quarantined instead of duplicated. |
| `repair.queue_search_grace` | `2m` | Observe grabs/imports for this long after a confirmed completed search. |
| `repair.queue_retry_delays` | `6h,24h,72h` | Delays after successive searches that produced no replacement download; at most 10 delays, each between 1 minute and 168 hours. |

The existing worker runs one Arr operation at a time. Once a job has requested a
replacement, it occupies a slot while the search/download/import is active.
A completed search with no observed replacement is rescheduled and releases its
slot. Jobs requiring manual attention also release their global slot, while
retaining their media/season guard against duplicate work. Jobs waiting for dispatch do not expire as pending imports.
Backlogs are kept in the job database and continue automatically when a slot is
available. A queued orphan already covered by an earlier import can consume a
dispatch slot for verification, but causes no additional search.

An independent observer checks explicit Arr command receipts, grab history, the
Arr queue, and imported file identities. A completed command alone does not prove
that no release exists: the displayed outcome is **search completed without a
replacement download**, after the grace period. Missing commands, API failures,
and timeouts remain unknown/error outcomes. Searches beyond their deadline need
attention; downloads/imports without progress for six hours also release their
slot and need attention. Download progress extends that stall deadline.

Scheduled retries persist across restart and use the same interval, batch, and
capacity controls as first attempts. Before another search, a read-only preflight
checks for a late download/import. Safe local search errors use shorter delays
(1, 5, then 30 minutes); uncertain remote mutations keep their reconciliation
receipts and are never blindly replayed. After the configured automatic retries,
the job remains visible for manual attention. **Retry now** makes a safe retry
eligible without bypassing dispatch limits.

### Library repair tracking

**Repair → Library repair** shows audit incidents with diagnosis, recovery state,
retry count, next eligible attempt, and per-file actions. It groups Sonarr files
by season, supports filtering/search/pagination, and retains findings when Arr
removes an old file during replacement. **Recheck**, **Repair**, **Retry now**, and
**Suspend/Resume** act on the selected incident. Suspension stops future attempts;
it does not cancel a download already running. Ambiguous remote actions are
reviewed/acknowledged in **Arr Reacquisition** before starting other work.

The observer attempts a library read after detecting a replacement import, when
the auditor is idle. Otherwise the next audit or **Recheck** validates it. An Arr
import is shown separately from **Readable**; only a successful read resolves the
incident. Recovery history is retained until explicitly removed through the
existing job-history controls.

Media links use the real Arr title slug. Set the optional **Browser URL** on each
Arr when its internal Docker hostname is inaccessible from your browser, for
example `https://sonarr.example.com/sonarr`. The API host stays unchanged.

Audit status and recovery status poll independently with a 10-second request
limit, automatic retries, and the last successful snapshot retained on errors.

Pause/resume is available in **Arr Reacquisition**, alongside queued/in-flight
counts and the next dispatch time. It holds new repair dispatches without stopping
the current audit, existing downloads/imports, or reconciliation of operations
already started. Explicit manual reacquisitions and stream-triggered recoveries
are outside this automatic repair throttle. Provider reinsertion attempts and
read-only checks made while producing jobs are also outside the dispatch limit.
The limit applies to jobs, not individual HTTP requests or indexers contacted.

Queue settings are editable in Configuration. Empty duration fields and zero
numeric fields use the defaults. Durations use Go duration syntax, such as `10s`
or `5m`; the interval must be at least `1ms`, the batch pause may be zero, and both
are limited to 24 hours. Negative counts are rejected.

The batch counter and next slot are saved atomically in `db/repair_queue.json`
before a new job can mutate an Arr. A restart or removal of terminal job history
does not reset the cooldown. A failure to persist a reservation blocks dispatch
and is shown in the queue status. Preserve the job database and this state file
when backing up the application.

The authenticated queue API is `GET /api/arr/reacquire/queue`. Pause or resume with
`POST /api/arr/reacquire/queue`, body `{"paused": true}` or `{"paused": false}`.

### Recovery progress in the UI

The Health Checker distinguishes **Queued** recovery requests from **Restored**
files confirmed readable immediately. A finished **Fix broken** run shows
**Submission complete**; recovery can still be running. Older run totals are
labelled **Recovery requested (legacy)** because the two outcomes were not
recorded separately.

The **Recovery progress** panel polls while jobs remain outstanding, including
after submission finishes. It shows queued, working, waiting for grab, downloading,
waiting for import, imported, needs attention, failed, and cancelled jobs, with a
link to the detailed Arr Reacquisition table. Imported means Arr confirmed a
replacement; it is not a new filesystem read test.

These live totals cover all retained repair jobs across runs, not a single scan
or a count of media files. Clearing or expiring terminal job history changes the
totals. Unavailable progress is marked stale and retried automatically.

## Configuration

```json
{
  "repair": {
    "enabled": true,
    "source": "arr",
    "schedule": "0 4 * * *",
    "workers": 5,
    "strategy": "per_entry",
    "recheck_interval": "168h",
    "arrs": [],
    "auto_repair": true,
    "library_audit": false,
    "queue_interval": "10s",
    "queue_batch_size": 50,
    "queue_batch_pause": "5m",
    "queue_max_active": 10,
    "queue_paused": false,
    "queue_search_timeout": "5m",
    "queue_search_grace": "2m",
    "queue_retry_delays": "6h,24h,72h",
    "verify_content": false,
    "notify_on_complete": false,
    "nntp_connection_percent": 20,
    "stop_schedule": "06:00"
  }
}
```

| Field                     | Description                                                                              | Default     |
|---------------------------|------------------------------------------------------------------------------------------|-------------|
| `enabled`                 | Master switch. When off, no scheduled sweep runs (single rechecks still work).           | `false`     |
| `source`                  | Where to enumerate from: `arr` (walk Arr media) or `managed` (walk managed entries).     | `arr`       |
| `schedule`                | Cron expression for the recurring sweep. Required when `enabled` is `true`.              | —           |
| `workers`                 | Number of concurrent probe workers.                                                      | `5`         |
| `strategy`                | `per_entry` (stop after first broken file in an entry) or `per_file` (probe all files).  | `per_entry` |
| `recheck_interval`        | How long a healthy entry's check stays fresh before it becomes a candidate again.        | `168h`      |
| `arrs`                    | Optional filter when `source=arr`. Empty list means all eligible Arrs.                   | `[]`        |
| `auto_repair`             | When `true`, broken Arr-managed files are deleted through Arr and searched again. When `false`, the sweep is detect-only. | `false` |
| `library_audit`           | Use concurrent library-path sample reads instead of provider entry probes for scheduled runs. | `false` |
| `verify_content`          | During NZB probes, also read each media file's head through the streaming stack and check for a valid container signature. Finds files whose articles exist but were assembled wrong. Downloads one article per file probed. | `false` |
| `notify_on_complete`      | Send a notification when a sweep finishes.                                               | `false`     |
| `nntp_connection_percent` | Percentage of NNTP connections the probe is allowed to use. Avoids starving downloads.   | `20`        |
| `stop_schedule`           | Optional cron expression, clock time, or interval. If a repair sweep is still running when this fires, it's stopped early. Leave empty to always run to completion. | — |

### Stop schedule

`stop_schedule` is useful when a repair sweep needs to finish (or get out of the way) before something else happens — for example, before your overnight maintenance window ends, or before peak-usage hours when probes would compete for bandwidth.

- The repair sweep is cancelled at the next firing of `stop_schedule`, mid-probe if necessary. Entries not yet probed are left as they were before this repair sweep (their existing health and `next_check_due_at` are untouched, so they're picked up again on the next scheduled run).
- The run is recorded as `completed` (not `cancelled`), with `cancel_reason` noting it was stopped by schedule.
- What happens to entries this repair sweep *did* manage to probe and found broken is controlled by `auto_repair`, same as any other repair sweep:
  - `auto_repair: true` uses Arr delete + re-search for eligible broken files.
  - `auto_repair: false` leaves them recorded as broken without triggering Arr repair.

#### Multi-day coverage

Each repair sweep probes due entries **oldest-checked-first** (never-checked entries first, then least-recently-checked, ...). Probing an entry updates its `last_checked_at` immediately, which moves it to the back of the queue for future repair sweeps.

This means a repair sweep scheduled daily with a `stop_schedule` (e.g. `schedule: "0 0 * * *"`, `stop_schedule: "0 9 * * *"`) makes guaranteed forward progress across days, as long as `recheck_interval` is comfortably longer than the time it takes to cycle through the whole library:

- Day 1, 00:00–09:00: probes the oldest N due entries (or however many fit in 9 hours), marking each one's `last_checked_at` as it finishes.
- Day 1, 09:00: `stop_schedule` fires, the repair sweep stops. The remaining entries are untouched and stay oldest in the queue.
- Day 2, 00:00: the next repair sweep's `due` set excludes everything probed on day 1 (their `last_checked_at` is now within `recheck_interval`), so it continues with the next-oldest N.
- This repeats until the whole library has been probed within one `recheck_interval` window, then the cycle restarts from the oldest again.

If a full repair sweep would take 2 days at 9 hours/day but `recheck_interval` is `168h` (1 week), this comfortably completes a full pass well before entries become due again. If `recheck_interval` is shorter than the time a full cycle actually takes, some entries may go stale before they're re-probed — increase `recheck_interval`, the daily window, or `workers` to compensate.



### Strategies

- **`per_entry`** — probe stops at the first broken file in an entry. Faster on broken libraries; sufficient when you only need to know "is this entry intact?".
- **`per_file`** — probe every file. Use when you want a complete broken-file list per entry (e.g. to drive a per-file Arr re-acquire).

### Sources

- **`arr`** — walks Sonarr / Radarr media, resolves each item to an entry through the symlink target, and probes that entry. Broken files are enriched with Arr identifiers so repair can call `DeleteFiles` + `SearchMissing` directly.
- **`managed`** — walks managed entries directly. Entries can be health-checked, but automatic replacement is available only for broken files that carry Arr identifiers.

## Workflow

1. The cron tick (or a manual **Run Now**) opens a new run.
2. Candidates are selected per the rules above.
3. For each candidate, the entry is marked `repairing` and probed by a worker.
4. NZB probes sample the configured percentage of distinct content articles. With `verify_content` enabled, they also read each media file's head and validate its container signature.
5. Definitive missing or corrupt content marks the file broken. Connection and provider errors remain `unknown` and never trigger replacement.
6. With `auto_repair` enabled, eligible broken files are deleted through Arr and a missing-item search is triggered.
7. The entry health and run progress are persisted as the sweep proceeds.

Background NNTP probes share the configured `nntp_connection_percent` pool so active streams retain capacity.

A failure to persist a single entry's health update is logged but never aborts the sweep.

## Sonarr season-pack replacement policy

In this fork, newly queued Sonarr health-check repairs use `season_pack_first`.
For torrents, the health checker first attempts to reinsert the original torrent
across the configured debrid providers. If that succeeds, no Arr replacement is
queued. Reinsertion uses cached content; it does not enable uncached downloads.

If reinsertion fails, the Arr job groups authoritative files sharing the original
download ID, then deletes those files through Sonarr. It performs a season release
lookup and accepts only eligible `fullSeason` releases for that series and season,
in Sonarr's returned order. The original torrent is excluded when its infohash is
available. Rejected releases and releases spanning multiple seasons are excluded.
If no acceptable pack is returned, the job sends `EpisodeSearch` for the affected
episode IDs. API failures or an uncertain grab outcome never trigger that fallback.

This policy also tries a season pack when only one episode remains associated
with the download. Jobs spanning multiple seasons fall back to `EpisodeSearch`.
Missing episode IDs prevent an episode fallback. Only currently indexed files
sharing the download are grouped; other copies of the season are not deleted.

`season_pack_first` deliberately does not fail grab history or blocklist the old
release: Sonarr's failed-download handling could otherwise launch a competing
automatic search before the pack decision. The episode fallback uses Sonarr's
normal selection rules. The existing `history_failed`, `command_search`, and
`interactive_best` manual strategies remain available. A manual pack-first option
is also available in Arr Reacquisition; it starts at replacement selection, without
reinserting the original torrent. Radarr behavior is unchanged.

Replacement remains asynchronous and does not resume a failed Plex playback.

For a complete sweep every twelve hours, use `enabled: true`,
`schedule: "0 */12 * * *"`, and `recheck_interval: "1s"`. A zero recheck interval
falls back to seven days. Keep `auto_repair: true` to enable repair after detection.

## Stop and disable

- **Stop** cancels the active run. In-flight probes return at the next checkpoint, the run is marked `cancelled`, and entries that hadn't yet finished probing revert to their previous status.
- **Disable** (`enabled=false`) cancels any in-flight run and unregisters the cron job. Per-entry health data is **kept**, so Browse badges stay meaningful and single-entry rechecks remain available.

## Singleton invariants

- At most one sweep runs at a time. Triggering a second one returns `409 Conflict`.
- A force-recheck on an entry that is already being probed by the active sweep returns `409 Conflict`.

### Examples

Run a sweep now:

```bash
curl -X POST http://localhost:8282/api/repair/run \
  -H "Authorization: Bearer YOUR_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"protocol":"all","unrestrict_link":true}'
```

Stop the active sweep:

```bash
curl -X POST http://localhost:8282/api/repair/stop \
  -H "Authorization: Bearer YOUR_API_TOKEN"
```

Force-recheck a single entry:

```bash
curl -X POST 'http://localhost:8282/api/repair/health/My.Show.S01/check' \
  -H "Authorization: Bearer YOUR_API_TOKEN"
```

Recheck a single Sonarr series and repair it if broken:

```bash
curl -X POST http://localhost:8282/api/repair/recheck/media \
  -H "Authorization: Bearer YOUR_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"arr":"Sonarr","media_id":"123","fix":true}'
```

## Browse page

Each entry row carries a health badge whose colour reflects the current status (healthy / broken / repairing / unknown / stale / unsupported). Hovering shows the last-checked time, broken-file count, and top failure reason. The row's action menu has **Recheck health**, and clicking the badge opens a side panel listing every broken file with its reason and Arr link.

The badges flip live during a sweep — entries move through `repairing → healthy/broken` as the workers report results, without needing to refresh after the run finishes.

## Per-Arr skips

Disable repair for specific Arrs:

```json
{
  "arrs": [
    { "name": "Sonarr", "skip_repair": true }
  ]
}
```

## Rate limiting

Probes against debrid providers respect a separate rate limit so they don't starve regular downloads:

```json
{
  "debrids": [
    { "provider": "realdebrid", "repair_rate_limit": "60/minute" }
  ]
}
```

For Usenet probing, `nntp_connection_percent` (above) caps the share of NNTP connections the health checker uses.

:::caution
With `auto_repair: true`, a sweep deletes the broken Arr file records and triggers a search for replacements. Verification of those re-acquires happens later — the Arr import is asynchronous and the badge flips to `healthy` once the replacement file is in place.
:::

## Troubleshooting

### Sweep takes too long

Increase `workers`, or raise `recheck_interval` so fewer entries become candidates each tick:

```json
{
  "repair": {
    "workers": 10,
    "recheck_interval": "336h"
  }
}
```

### Sweep is too aggressive

Lower `workers`, lengthen `schedule`, or set `auto_repair: false` to run detect-only and review brokens before fixing.

### One entry keeps flipping broken

Open its detail panel from Browse to see the broken-file list and reason. For Arr-sourced entries, trigger fixes through the Arr integration without waiting for the next sweep.

## Migration from v1

The job-based repair system (`repair_jobs`, `repair_keys`, the **Add Job** UI) has been removed. On first boot of the new system the legacy buckets are dropped, and existing recurring schedules do **not** carry over — re-enable repair once with the new config.

Per-entry health records (`repair_state`) are forward-compatible; new fields default to empty and populate on the next probe.
